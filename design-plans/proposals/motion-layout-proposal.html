Motion & Layout Standards

A modern motion and layout system for Typed, grounded in what the app already does. Everything below is a proposal — nothing in the product changes until you accept items.

01Motion tokens — one system instead of 9 one-offs

Today the app hand-picks 200ms, 150ms, 180ms, 260ms… with default curves. Proposal: four durations and three easings in one AppMotion class, used everywhere.

TokenValueEasingUsed for
fast120 msaccelerateexits, hover states, pressed
base200 msemphasizedselection, hover lift, toggles
slow320 msdeceleratepanel reveal, view switch, sheets
page450 msemphasizedmobile editor open/close, onboarding

Every animation also collapses to zero when the OS "reduce motion" setting is on — currently ignored by the app.

05Home — staggered section entrance

Home currently paints all sections at once. Proposed: 45ms stagger per section, 320ms rise-and-fade, once per app start. Subtle, not showy:

06Curves — why “emphasized”

Linear motion feels mechanical; overshoot feels toy-like. Material’s emphasized curve (fast start, gentle landing) is the modern default for UI pushes — proposed for the sidebar and all panel reveals:

linear (avoid)
emphasized (proposed)
overshoot (avoid)

08Layout tokens — grid, radii, type

BRANDING.md promises an 8px grid; the code uses 2/3/7/9/11/13/26px ad-hoc values, radii range over 8 values, and font sizes include 9.5/10.5/11.5/12.5. Proposal: three token sets, applied without changing any screen’s structure.

Acceptance checklist — pick any subset
  • 01 Motion tokens — foundation; required by everything else
  • 02 Command palette entrance — fade + rise + scale
  • 03 View switches — slide & fade between sections; mobile list ↔ editor
  • 04 Card hover lift — desktop hover lift + press scale
  • 05 Home stagger — once-per-start section entrance
  • 06 Emphasized curves — sidebar + panels use the standard curve
  • 07 Skeleton loading — shimmer rows replace the static splash
  • 08 Layout tokens — spacing / radius / type consolidation
  • Accessibility — all motion respects the OS reduce-motion setting
Visual proposal only — no product code was changed. Demos are CSS stand-ins for the Flutter implementation (same durations/curves). Everything ships behind the reduce-motion check.
